# 游戏 UI 设计：先分任务与表征，再选风格

本文件是给制作 agent 的设计决策框架。它依据原始研究、作者论述、平台指南和标准解释整理；**不是学界统一分类，也不是对任何游戏整体 UI 质量的认证**。来源及证据范围见 [14 条来源记录](ui-foundation-sources.json)，机器可读维度见 [ui-taxonomy.json](ui-taxonomy.json)。

## 原有六套配方为什么不够

`wood-paper`、`dark-stone`、`holo-terminal` 等主要描述材质、图形和气氛。同一个木纸主题，可以服务背包、商店、对话、任务日志；这些系统的对象、决策、状态与输入路径不同，换皮并不能产生正确设计。

需要分别记录四个层级：

| 层级 | 回答的问题 | 例子 |
|---|---|---|
| 游戏系统 | 规则、对象和状态怎样变化？ | 交易：库存、价格、玩家资金、购买结果 |
| 玩家任务 | 此刻要做什么决定？ | 先比较工具，再决定买几个 |
| 界面与流程 | 在哪里观察、操作和恢复？ | 商品列表 → 对比详情 → 数量与总价 → 结果 |
| 组件与内容 | 用什么承载信息和操作？ | 商品行、数量步进器、差值、缺钱说明、焦点框 |

“背包”是系统与任务入口；“全屏页”“弹窗”“HUD”是呈现方式；“木纹”“拟物”“平面”是视觉或表征选择。它们不应挤在一个互斥风格列表中。

## 一套可以执行的决策顺序

```mermaid
flowchart LR
  A[系统规则与玩家任务] --> B[对象、成本、效果、风险]
  B --> C[同时比较与按需展开]
  C --> D[空间、叙事、时间、输入]
  D --> E[物件隐喻与视觉语言]
  E --> F[状态与恢复路径]
  F --> G[真实内容和设备验证]
```

这个顺序是本库的编辑综合建议。已有项目不必推倒重做；只补齐本次任务缺少的决策。不能为适应界面而擅自改价格、物品规则、暂停行为或存档语义。

## UI 的“风格”至少要分开看

### 视觉语言：拟物并不只是纹理

以下是工作标签，可组合使用，并非严格的历史流派边界。

| 方向 | 具体设计对象 | 适用判断 | 常见代价 |
|---|---|---|---|
| 物件式拟物 | 书、票据、工具台等物件的结构与操作隐喻 | 物件是否真的帮助理解当前任务？ | 额外翻页、面积浪费、操作入口含糊 |
| 材质暗示 | 木边、纸底、金属接缝；内容仍是可伸缩布局 | 能否维持世界气氛，又容纳真实文字？ | 纹理侵入正文、装饰抢焦点 |
| 平面图形 | 色块、轮廓、图标、文字与留白 | 操作、分组与层级是否仍然明确？ | 过度弱化控件线索，按钮看起来像静态文字 |
| 强图形/装饰表达 | 夸张字体、斜线、剪影、纹章与节奏 | 是否适合当前情绪和使用频率？ | 高频操作被转场打断，比较信息难对齐 |
| 文字/终端表达 | 列表、数字、符号、格线和等宽节奏 | 信息本身是否以精确关系和状态为主？ | 字符难辨、学习负担、中文挤压 |

浮雕外观不是“可操作”的充分证据，平面外观也不意味着不可操作。应检查玩家能否看到动作线索、预期结果并理解状态。Norman 将可感知的线索称为 signifier；它与实际可执行的动作关系不能混为一谈。[Norman：Signifiers, not affordances](https://jnd.org/signifiers-not-affordances/)

尤其不要引用“平面 UI 一定慢 22%”来否定风格。NN/g 的研究比较了网页目标定位中的强弱可点击线索，涉及 71 名参与者和 9 对页面；并未测量完整游戏任务。其作者随后明确解释，问题在于弱或缺失线索，不能将平面设计整体判坏。[原实验](https://www.nngroup.com/articles/flat-ui-less-attention-cause-uncertainty/)，[方法与争议说明](https://www.nngroup.com/articles/response-criticisms-flat-design/)

### 叙事与空间：另两个问题

分别问：**表示物是否属于虚构世界？位置是否属于场景空间？** 下表是便于工作的简写。

| | 世界锚定 | 屏幕叠加 |
|---|---|---|
| 表示物在虚构中存在 | 场景中的价目板、角色设备显示 | 角色日记/手机的独立阅读页 |
| 表示物面向玩家 | 地块高亮、对象头顶标记 | HUD 数字、设置菜单 |

这些例子是设计推演。材质不能决定象限：木框弹窗未必是世界物件；场景里的电子面板也可以采用平面图形。

Fagerholt 与 Lorentzon 的论文讨论了 diegesis 的灰区，并把 fiction 与 spatiality 分开；它还区分 **meta-perception**（如感知状态的模拟）与 **meta-representation**（虚构物件的屏幕化表示）。因此不宜把染红屏幕和角色手机都简化为同一种“meta”。论文也明确反对“全世界内 UI 自动更沉浸”的推断。该研究主要针对 FPS，迁移到俯视游戏需要重新验证。[原论文，第 7、10 章](https://publications.lib.chalmers.se/records/fulltext/111921.pdf)

### 还需记录的五个维度

叙事、空间与视觉语言之外，以下维度共同决定界面是否适合当前任务：

- **信息表征**：图像负责认物、图式负责关系、数值与文字负责精确条件；必要时组合。
- **注意需求与密度**：扫视状态、集中比较、长期规划需要不同布局；密度高不等于设计差。
- **出现方式**：常驻、情境出现或按需打开；消失后能否找回重要信息。
- **世界时间**：继续、暂停/减速、回合约束；这是玩法合同，不由皮肤决定。
- **输入与导航**：指针、焦点命令、多输入切换；选择、焦点与已执行结果分别表示。

这八个维度能够组合，但并非统计独立。例如世界锚定会受镜头与遮挡约束，物件隐喻会影响内容面积。应记录选择理由和代价，而不是给一个“拟物=8分”的总分。

## 内容怎么设计：从玩家决策反推字段

先写一张内容合同，再画边框。以下是整理者提出的工作结构：

```text
任务：玩家要决定什么？
对象：正在操作哪一件物品、哪一个角色或哪一块地？
现状：持有量、当前选择、已装备、进度或当前限制。
行动：可执行的主要动作，使用明确动词与对象。
代价：费用、材料、时间、容量或机会成本。
结果：预计变化；区分预览、排队和已经生效。
条件：为什么可用、不可用、锁定或未知？
恢复：取消、返回、撤销或错误后的下一步。
显示规则：谁先看见什么，哪些字段必须同时比较？
```

例：购买锄头时，名称、当前/新工具差异、单价、数量、总价、购买后余额与容量限制应支持同一决定。长背景故事可进入详情。另一任务若是考据物品故事，则故事本身可能是主体，不能机械地隐藏“长文字”。这体现任务相关的信息取舍，不是固定内容模板。

“按需展开”适合低频和深入内容；若把成本与效果藏在互相排斥的页签中，就可能迫使玩家记忆后再比较。[NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)

## 从理论转成实际检查

| 设计原则或问题 | 在游戏里如何落实 | 需要什么证据 |
|---|---|---|
| 操作和结果有语境 | “购买 3 个”旁边显示总价、余额与阻挡原因 | 真实数据下的购买流程 |
| 减少无谓记忆 | 装备差值同屏、属性顺序稳定；保存选择与滚动位置 | 对比任务而非单张空白模板 |
| 状态可见与可恢复 | 区分预览/提交/完成；失败能重试或返回 | 成功、失败、取消流程 |
| 阅读是实际显示问题 | 用最长真实中文、数字和目标设备截图；提供可读字体/缩放 | 最终屏幕字形、缩放后布局 |
| 焦点可预测 | 初始焦点、方向邻居、弹窗关闭返回点明确 | 键盘/手柄完整操作记录 |
| 关键语义不只靠颜色 | 缺料同时用数量、标记或文字；警报按需要提供其他感官线索 | 灰度/色觉与静音等对应测试 |
| 输入上下文不冲突 | 打开背包时确认键不会同时攻击；关闭后恢复正确映射 | 打开→操作→关闭→继续世界 |

上表是应用建议，依据包括 [Nielsen 启发式](https://www.nngroup.com/articles/ten-usability-heuristics/)、[XAG 114 语境](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/114)、[XAG 101 文字](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/101)、[XAG 112 导航](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/112)、[XAG 103 多感官线索](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103)与 [Steam Input 状态层](https://partner.steamgames.com/doc/features/steam_controller/action_set_layers)。平台指南和具体 API 不等于本项目已经满足它们。

对比度、目标大小也要保留单位和范围：WCAG 普通文字最低对比为 4.5:1，大字为 3:1；指针目标规则中的 24×24 是 **CSS 像素**，且有例外。这不是要求把像素游戏源素材一律画成 24×24，也不能据此宣称游戏整体合规。输入尺寸、可视尺寸、逻辑像素与最终显示尺寸应分开记录。[对比度解释](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)，[颜色语义](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)，[目标大小解释](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

不要把常见认知定律变成装饰性的论据：这里没有提供将 Hick、Fitts 或“7±2”直接换算成按钮数、字号、动画时长的规则。选择数量、目标距离、学习经验和错误代价都需要具体任务证据；若要做定量推导，应另查原实验、任务假设与适用范围。

## 用一个乡村游戏任务检验这套框架

假设任务是“选菜谱，确认材料，安排制作”。这是未实现的设计推演：

1. **系统**：菜谱、持有材料、工具条件、生产队列与产物去向。使用项目真实规则。
2. **决定**：做哪道菜、做几份、会消耗什么、缺什么、何时完成。
3. **信息**：列表里显示名称与关键状态；详情同屏显示材料需求/持有、份数与总消耗。仅靠红绿图标不够。
4. **空间与时间**：灶台附近可有交互提示；打开菜谱后是否暂停须按游戏规则决定。多人世界若持续运行，需要清楚的退出方式。
5. **视觉**：可选纸面配方册，也可用平面网格。若做成书，不应强制每查一次材料都播放长翻页。
6. **输入**：手柄能从菜谱列表到份数与制作按钮，再返回原菜谱；鼠标有等价入口。
7. **状态**：未解锁、缺料、队列满、制作中、完成、取消、没有菜谱分别有真实语境。
8. **验证**：最长中文菜名、满队列、极少/极多材料、目标显示尺寸、控制器切换和取消后的状态保留。

可见，“拟物菜谱”只是第 5 步的一部分，不是整个系统设计。

## 怎样才算更严谨的审核

把审核记录分成四层，不用一个审美分数代替全部结论：

1. **可测技术事实**：像素尺寸、实际字号、文本截断、对比度、焦点是否可达。说明测量方法和条件。
2. **可观察行为**：玩家是否找得到对象、理解代价、正确完成任务、从失败恢复。记录任务与输入设备。
3. **视觉设计判断**：层级、材质、节奏、世界协调与品牌表现。用具体屏幕区域和反例支撑，标为设计评析。
4. **体验假设**：是否更沉浸、降低认知负荷、适合初学者。未做对应研究时标为待验证假设。

比较两个方案时，固定同一任务、内容、设备和代表性状态，再观察完成率、错误类型、查找/完成时间、焦点绕路以及玩家对结果的理解。样本数、成功阈值和重要差异应按实际研究问题设定；不预先发明一个通用“达标分”。

静态截图适合检查层级与材质，不能证明关闭弹窗会归还焦点，也不能证明玩家觉得沉浸。官方截图来源明确，也仍可能是旧版本或宣传状态。原有案例应继续保留“画面事实 / 设计判断 / 未验证项”的分隔。

## 对本库的重新定位

原有六套 UI 配方保留为可调整的视觉主题起点；它们不应冒充六种完整 UX 体系。本次新增八维分类用于记录设计选择，系统模式用于组织任务与内容，真实案例用于提供可观察的参照。三者一起使用，才能回答“什么系统、哪些界面、显示什么、怎样操作、为何选这种视觉语言”。

自我限制：这是一份经来源核对的设计综合，不是系统性文献综述或元分析；没有使用者招募、控制实验或真实项目运行数据。分类允许灰区与混合，具体主题归类仍需要实际画面和项目设定。
