# 像素游戏UI：风格、布局与实际可用性

在用户需要菜单、背包、对话、商店、设置、战斗HUD或建造面板时读本文件。完整参数在 [ui-profiles.json](ui-profiles.json)；场景风格入口在 [style-design.md](style-design.md)。这里的流程由整理者依据 `themed-uiux` 的任务、文字、组件和渲染检查原则编写，不依赖安装该skill才能执行。

## 先确认玩家当前要做的决定

先写一句真实任务：例如“比较两件工具并决定购买哪件”，然后确定必须同时看到的物品、价格、效果、资源缺口和主动作。按这个读序安排界面，不按代码模块划分一排页签，也不要把每项信息都包成独立网页卡片。

对于已存在界面，只修改任务所需范围。保留实际游戏机制、存档、名称、数值及状态来源；不要为适配新皮肤捏造稀有度、费用或进度。

## 选择与世界相容的UI配方

| UI profile_id | 视觉角色 | 常见适配 |
|---|---|---|
| `wood-paper` | 木边、纸面、安静文字区 | 乡村生活、自然题材、手账 |
| `compact-handheld` | 简线、指针、少色阶、清楚点阵 | 小画布、限色、双色 |
| `bold-arcade` | 强色块、短标签、明显形状反馈 | 动作游戏、得分和快速重试 |
| `ornate-fantasy` | 书页、皮革与少量金属纹章 | 装备比较、任务日志、对话 |
| `dark-stone` | 暗石/铁板与高可读信息层 | 暗色地牢、生命与警告 |
| `holo-terminal` | 硬边、少量发光、安静数值区 | 科幻终端、扫描、建造 |

沿用项目已确认规范。颜色、线重、光源和图标材质可以与世界呼应，但文字层的可读性、显示网格与命中区域要单独确定。暗色游戏不要求文字也暗；掌机风不要求中文小到无法辨认。

## 组件规格最少要包含什么

对本次确实需要的组件记录以下字段，不必建立无用的完整设计系统：

```text
组件与任务：例如背包物品槽，用于选择并查看/使用物品
外观素材：图像来源、逻辑尺寸、九宫格或三段式边界
内容：图标区、名称区、数量区、最长真实文本
状态：normal / hover / pressed / selected / focus / disabled
额外结果：error / loading / empty（如适用）
输入：鼠标、触控、键盘、手柄；各自确认/取消规则
命中区域：最终显示尺寸、边界与相邻控件间距
布局：最小内容尺寸、扩展方式、重排/分页策略
运动：开启时的反馈；减少运动/关闭时的静态结果
```

选中状态与键盘焦点可以同时存在，必须能分辨。不可用状态应保留可读标签和解释条件；错误应告诉玩家发生了什么和如何继续。加载只显示真实进度或不确定等待，不把装饰扫描线伪装成百分比。

## 九宫格与素材分层

![Saint11 九宫格技术图：保留角部，单独处理边和中心](../library/assets/supplement/UI-001/UI-9-Slice.gif)

图源：[Pedro Medeiros / Saint11 固定提交](https://github.com/saint11/Saint11Tutorials/blob/ce1393eb2c46441d917134a9fd52e15575ee10a7/UI-9-Slice.gif)，[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)。这是九宫格技法图，不是任一主题的完成界面。中文整理见 [UI-001](../library/tutorials/supplement/UI-001-nine-slice.md)。

把图像角部、边条、中心分开。角花、钉子、接口等应放在固定切片；可重复边条先做接缝检查；文字与动态数字始终是独立内容层。实际把面板拉宽、拉高、缩到最小支持尺寸，检查装饰是否被压扁或切半。

Godot的 `NinePatchRect` 保留角部，轴向模式决定边与中心如何伸展。选择 `TILE` 时源纹理需要无缝；`TILE_FIT` 仍可能拉伸图块，不能因使用九宫格就断言像素没有变形。对有纹理的像素面板应显式核对模式，而不是依赖默认值。[Godot 4.5 NinePatchRect](https://docs.godotengine.org/en/4.5/classes/class_ninepatchrect.html)

## 文字、布局和命中区域分开检查

- **文字资产：** 保留字体许可，验证真实字符覆盖。正文、标题、数字可以有不同角色，但同一角色的fallback应可预期。不要混入不协调的缺字替代字形。
- **实际内容：** 使用最长中文物品名、多行说明、负号/单位、最大合理数值和禁用条件填充原型。装饰不能占用内容区域。
- **最终尺寸：** 记录父级缩放后的显示字号、行高和图标尺寸。出现拥挤时先重排、扩容、分页或详情视图，不一味缩小文字。
- **命中范围：** 小图标可配更大的透明命中区域，但相邻区域不能重叠。分别在鼠标、触控或手柄目标上测试，而不是从图片尺寸推断可用性。

文字对比可把普通正文4.5:1、大型文字3:1作为起点；大型文字应按实际显示尺寸和字重判断，不能只因控件名叫“标题”就放宽。纹理和半透明底下应检查最不利背景。此项检查不等于整个游戏满足无障碍标准。[W3C WCAG 2.2：文字最低对比](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

## 键盘与手柄路径

进入面板时给出明确初始焦点，定义四方向邻居、确认、取消和关闭后返回位置。当前控件隐藏或消失后，主动把焦点移到合理目标。Godot可为 `Control` 配置焦点邻居；缺省猜测在复杂界面中可能不符合玩家预期。UI导航动作不应同时触发世界移动。[Godot 4.5：键盘/手柄导航与焦点](https://docs.godotengine.org/en/4.5/tutorials/ui/gui_navigation.html)

至少实际走一次“打开→移动焦点→改变选择→执行/取消→关闭→回到原状态”的完整路径。模态界面应阻止底层误操作，关闭后能继续原任务。

## 验证用例和交付

| 证据 | 检查内容 | 不足时怎样报告 |
|---|---|---|
| 组件状态联系表 | 正常、焦点、选中、禁用、错误等能否区分 | 缺失状态列为未制作/未检查 |
| 真实内容截图 | 文字、数字、图标、边框是否冲突 | 标明哪个屏幕、组件、尺寸与具体文本 |
| 世界叠加截图 | HUD是否遮挡角色或危险；图标材质与光照是否协调 | 不能只展示孤立透明面板 |
| 实际交互 | 焦点、确认/取消、滚动、重开是否正确 | 静态设计不称为已验证可交互 |
| 运动关闭状态 | 结果可读、关键提示不靠动画 | 没有运行这一状态则明确未检查 |

对布局变化，检查当前尺寸、较小支持尺寸和较大尺寸；局部修复只选择能揭示该问题的用例。保存项目实际截图与说明，图像联系表或脚本指标都不能替代交互验证。

可交付一份明确的小包：本次采用的UI配方与项目覆盖值、需要的组件状态、带真实文字的画面、素材/字体来源、实际检查记录与剩余问题。不要把模板填完或代码编译通过写成“美术一致性已通过”。
