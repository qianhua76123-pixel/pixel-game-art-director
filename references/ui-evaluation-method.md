# 游戏 UI 审查：让结论对应证据

本页是整理者为像素游戏制作编写的审查协议。它采用启发式审查、任务走查与真实用户测试的区分；不是认证标准，也不输出缺少依据的“美术 95 分”。

## 先确定正在评价哪一件事

同一屏界面可以视觉统一却难以操作，也可以效率高但不符合世界气质。分别记录任务可完成性、信息可理解性、视觉表达、可访问性与技术正确性。不要把它们压成一个平均分：一次不可恢复的误售，不能由漂亮边框抵消。

| 证据类型 | 可支持的判断 | 不能由此推出 |
|---|---|---|
| 官方规范/开发者说明 | 设计原则、实现约束或作者明确解释 | 所有玩家在这个产品里都体验良好 |
| 截图/静态稿 | 空间分组、文字层级、可见状态、装饰分布 | 动态可读性、焦点路径、交互成功率 |
| 可操作原型走查 | 此设备/输入/构建上的完整任务与恢复路径 | 新玩家一定能发现同一路径 |
| 目标玩家任务观察 | 观察样本中的完成、错误、理解与困难 | 未测试人群或条件下同样成立 |
| 机器测量 | 明确规则的尺寸、alpha、色值、溢出等 | 语义清楚、风格一致或整体无障碍通过 |

启发式审查适合提早发现风险、确定测试重点，仍需以使用者行为验证。认知走查沿任务步骤检查新用户是否知道该做什么、能否发现动作、理解对应关系和结果。[NN/g：启发式审查](https://www.nngroup.com/articles/how-to-conduct-a-heuristic-evaluation/)、[认知走查](https://www.nngroup.com/articles/cognitive-walkthroughs/)。

## 从一条真实任务开始

以下是本库原创示例，不是已运行的测试：

> 玩家有一组任务道具和普通收获物，希望卖掉普通作物、保留任务所需数量，并确认出售后还够购买种子。

先冻结测试条件：构建版本、存档夹具、资源初值、商店机制、目标设备、窗口与显示倍率、语言、输入设备、运动设置。不得为了界面好排而改变价格、任务条件或玩家已有存档。

然后分别记录：

1. **发现**：能否从世界找到交易入口；第一次进入是否知道卖什么、向谁卖。
2. **理解**：持有量、任务保留量、单价、出售数量、合计与交易后余额是否能同时比较。
3. **执行**：选择数量、确认、撤回/退出；手柄不依赖悬停，鼠标不受装饰遮挡。
4. **结果**：余额和数量更新是否真实；交易成功、失败、无货或资源不足是否可区分。
5. **恢复**：取消后位置/选择是否合理；断开输入或弹出设置后能否继续；不可逆动作的后果是否事先清楚。

## 八个独立审查面

| 审查面 | 寻找的具体问题 | 最低证据 |
|---|---|---|
| 玩家决策 | 缺少成本、条件、效果或不可逆后果 | 真实规则与任务内容对照 |
| 信息组织 | 同一次比较被拆到互不相见的页面；低重要信息抢焦点 | 最密集内容截图 + 决策走查 |
| 表意与映射 | 装饰像按钮；颜色是唯一警示；图标含义靠猜 | 图标/标签/状态表与理解观察 |
| 交互与反馈 | 焦点等同选中；操作重复提交；结果无反馈 | 打开→选择→执行/取消→返回的运行证据 |
| 视觉与世界 | 材质、线重、字形和色彩角色失配；HUD遮挡行动 | UI叠加真实世界画面 + 同倍率组件对照 |
| 内容与本地化 | 最长中文、负号、单位、数量、换行或缺字出错 | 真实边界内容，不用随机占位文字 |
| 适配与访问 | 重映射后提示过时；输入模态混用；运动关掉后丢反馈 | 支持设备/输入/设置组合的实际检查 |
| 技术规格 | 九宫格角部拉伸、像素倍率混杂、alpha污染 | 明确项目合同与源图测量 |

## 报告格式与严重度

每个问题写 `屏幕/状态/证据路径 → 观察 → 对任务的影响 → 修复假设 → 复验方法`。分离“看到的事实”和“推测的原因”。结果使用 `OBSERVED_PASS`、`OBSERVED_FAIL`、`UNDETERMINED`、`NOT_APPLICABLE`；仅对实际覆盖的条件下结论。静态稿中的交互项必须是 `UNDETERMINED`。

本库采用的严重度是项目排期工具：阻断任务或造成无法接受损失；能完成但反复出错/明显受阻；轻微效率或一致性问题；纯偏好。它不是通用定量量表。高后果问题单独处理，不以平均分稀释。

可记录完成率、非预期动作、回退次数、帮助需求与任务耗时，但先定义任务、计时边界、失败判定和目标人群。比较两版时尽量保持任务和设备一致，记录学习效应；不要给所有 UI 设任意的“三秒以内”或固定点击次数。口述、辅助提示等研究方法会影响耗时，应写入报告。

## 检查表不等于用户研究

涉及无障碍时，应让相应目标用户参与并结合技术规范检查。少数人的反馈不能外推至所有有相似或不同需求的人群，报告必须写出样本与范围。这里借用 W3C 的评价方法；其网页指南不是整款原生游戏的认证依据。[W3C：让用户参与无障碍评估](https://www.w3.org/WAI/test-evaluate/involving-users/)。

本库的案例分析目前主要属于静态观察；多 agent 复核能减少遗漏，但不等于多个真实玩家的独立实验。没有运行、没有用户观察的部分继续保留未验证标记。
