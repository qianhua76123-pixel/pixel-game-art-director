# 摆放与动线确认基准

在制作、扩展或复盘世界场景、建筑组、场地与可互动物件时阅读本页。本页说明如何把项目的摆放与动线写成可叠加的审查层，并在场景计划和合成稿上确认类型要素齐全、来路走得通、门前和站位没有被占。它不替代 [视角与透视确认基准](camera-baseline.md)、[一致性检查](consistency-review.md) 或 [主题合同](theme-cohesion-contract.md)，也不给布局自动打分。审查叠加层只用于审查，不画进游戏成品，也不能用来给模型当参考图。

若仓库里已有 [视角与透视确认基准](camera-baseline.md)，先确认机位，再查摆放；本页不重判消失点。该页可能随另一份补丁进入主分支，若当前检出里还没有，不要把它写进尚未填写的投影合同里顶替本页。

现有美术规范可以写尺度和锚点，但若只留下“留出空地”“走得通”这类空泛描述，审查时没有可对齐的路宽、门前净空和类型要素清单，门开进水里、主路突然收窄、该有院门的院子没有围墙，就只能等整张场景拼完再凭印象判断。

## 1. 先把布局写成可出图的合同

在批量摆放世界场景之前，先填 [美术规范模板](../assets/templates/art-bible.json) 的 `layout`。未确认的字段保持 `null`，不能由模板或模型提示词猜一个路宽或门前空地。格宽可以与 `projection.baseline.grid_unit_px` 相同，也可以在 `layout.grid_unit_px` 单独写出；两处都有值时以 `layout` 为准，矛盾时先停下来，不要默认为新生成图是对的。主题合同不要为此新增关键字段。

至少要能回答下面这些问题，才能画出审查叠加层。场景计划是按场填写的补充文件，不写进规范模板的默认值里。

| 字段 | 要写清的内容 | 不写清楚时会发生什么 |
|---|---|---|
| `grid_unit_px` | 一格的逻辑像素；可与投影基准的格宽相同 | 路宽、净空和占地无法画到同一套格子上 |
| `character_footprint_tiles` | 角色占地，单位是格，例如 1×1 | 站位和净空对不齐人能站住的位置 |
| `path_widths` | 主路、巷、桥或石阶的宽度，单位是格 | 必经之路被道具或岸线悄悄收窄 |
| `door_clearances` | 住宅门、公共门前要留出的净空，单位是格 | 门前堆着花丛或货箱，看上去像能进，实际站不住 |
| `building_gap` | 建筑之间的最小间距 | 两栋房子贴死，走道只剩一条缝 |
| `building_to_map_edge` | 建筑到画布或地块边缘的最小距离 | 屋脊或墙根被画框切掉 |
| `building_to_water` | 建筑基础到水面的最小距离。埠头、码头、桥梁作为临水例外，必须带可走的石阶或护栏，并写进 `building_to_water_exception` | 小屋地基泡在水里，或码头没有下岸的踏步 |
| `interact_gap` 与 `reserved_stand_tile` | 可互动物件之间的间距，以及是否在目标前留出一格站位 | 石碑、招牌或宝箱贴在墙根，人站不到交互点 |
| `cluster` | 一簇最多几件、半径、簇与簇或簇与路的间距 | 植物和碎石沿路铺成一条墙 |

每一场还要另写一份场景计划，至少声明：

- 场景类型（例如临水埠头、门院）
- 该类型必有的类型要素
- 主路：入口 → 路线 → 目的地（并给出中心线，单位是逻辑像素或格）
- 地标或指引物（weenie）
- 站立点

接头可以另写，不是必填：在场景计划的 `joints` 里记下哪一段墙、篱或绿篱要接到哪一个门、门洞或立柱。不写进规范模板的默认值。没写就略过，不能由模板补一组接头，缺了也不拒绝出图。

必填字段仍为 `null` 时，脚本应拒绝出图并说明缺什么，不能猜一个路宽或补一个院门。

## 2. 审查叠加层不是场景里的线

审查叠加层是一张透明图，叠在原尺寸或整数倍近邻放大的素材、联系表和场景合成稿上。推荐分色，避免和视角基准线或画本身混淆（视角基准线已使用青网格、黄铅垂线、品红尺度尺和白线框）：

- 道路走廊（橙）：按已声明的宽度，沿主路中心线画出等宽条带。正交项目里走廊上下一样宽，**不要画成向深处收窄的梯形**。
- 门前净空（绿）：住宅或公共门前按合同留出的空框，框内不应有道具或植物。
- 站位占地（紫）：在已声明的站立点画角色占地记号，表示这块地要留给站的人。
- 地标记号（红）：指引物或目的地的位置，用来核对主路是否通向它。

代码可以画出这张审查叠加层，也可以在编辑器里做同样的调试层；二者都不是设计图，不能进正式画面，也不能用来给模型当参考图。

用本 skill 的脚本从已填写的规范和场景计划生成叠加层：

```bash
python3 scripts/placement_baseline.py --bible /path/to/art-bible.json --plan /path/to/scene-plan.json --out /tmp/placement-baseline.png
python3 scripts/placement_baseline.py --bible /path/to/art-bible.json --plan /path/to/scene-plan.json --under /path/to/scene.png --out /tmp/placement-baseline-on-scene.png
python3 scripts/placement_baseline.py --bible /path/to/art-bible.json --plan /path/to/scene-plan.json --prompt
python3 scripts/placement_baseline.py --demo --out /tmp/placement-pass-vs-fail.png
```

字段仍为 `null` 时，脚本应拒绝出图并说明缺什么，不能默认为某种路宽或场景类型。`--under` 把透明叠加层叠到一张已有原图或场景合成稿上，得到的仍是审查对照图，不打分，也不表示通过。底图与叠加层同尺寸时直接叠。一边正好是另一边的整数倍时，只做最近邻缩放再叠，不拉伸，也不做双线性缩放。对不上、又不是整数倍时，脚本拒绝并说明原因，不写文件。比画布小的单件不会自动找位置摆进去；先把它铺到一张与叠加层同尺寸的画布上，再叠加。`--prompt`（同 `--print-prompt`）只按已填写的字段打出一段可粘贴的摆放条款，空字段略过，不替项目补一个路宽或院门；场景计划一旦传入，未填写的场景类型也应拒绝。计划里若写了 `joints`，条款只列出接头名称和两端构件，供人核对；叠加层不画这些接头，不测量墙端和立柱之间的缝，也不据此通过或失败。未填写则略过，不猜一组接头。不加 `--out` 时不画图。若提供可选的可行走蒙版 `--walkable`，脚本只做灌水并报告哪些声明点可达或不可达，这是数据核对，不是画风或布局评分，也不要把这次输出写成通过或失败。示例合同、场景计划和示意叠加层见 [placement-baseline 示例](../examples/placement-baseline/README.md)。该脚本只负责把已确认的摆放合同画成走廊或叠到指定图上，不给图像自动判定通过或失败。

## 3. 何时叠、怎样看

1. 世界或场景成组出图前，先冻结合同，并为这一场写好场景计划。同一项目修订只保留这一套路宽和净空，不按单件另发明一个尺度。
2. 若存在 [视角与透视确认基准](camera-baseline.md)，先叠视角基准线，确认没有混用机位或意外消失点，再叠本页的摆放层。本页不重判道路是否向上收窄；那是视角页的结论。摆放层要看的是：这条已声明的走廊有没有被堵住、有没有窄于合同、有没有通向目的地。
3. 提示词引用同一合同：写清路宽、门前净空、必有类型要素和主路。不要在每个任务里重写一套间距。需要粘贴时用 `--prompt` 从已填写的规范和场景计划打出条款，空字段略过。示例合同打出的是：`摆放：基准：480×270，格宽 16 逻辑像素。角色占地：1×1 格。主路宽：3 格。巷宽：2 格。桥或石阶宽：2 格。门前净空：住宅 3×3 格，公共 4×4 格。建筑间距：2 格。建筑距地图边：1 格。建筑距水：2 格，埠头、码头、桥梁须有石阶或护栏。互动物间距：1 格。留出站立格：是。簇：最多 5 件，半径 3 格，簇距 2 格。场景类型：gate-courtyard。必有类型要素：gate-opening、boundary-wall。主路：south road → gate opening → courtyard landmark。地标：stele。站立点：stele-view。接头：west-gate-post（boundary-wall → gate-opening）、east-gate-post（boundary-wall → gate-opening）。`
4. 先按场景计划核对应有的类型要素是否出现，再看整张合成。只看单件合格不够。门院类型要有可通行的门洞，以及作为边界的围墙或篱笆；临水埠头类型要有从陆地来的通路、可走上去的石阶或坡道，以及面向这条来路的埠头或码头。墙、篱或绿篱若要接到门、门洞或立柱，再看两边的实体有没有真正接上。
5. 在最终显示倍率下看一次动线和净空；缩略全图只能看布局，不能代替原尺寸核对。

生产时，石阶必须能读成可攀爬：踏面要分开，宽度不小于已声明的桥或石阶宽度。画面上画了的门要么走得到，要么明确封死（墙、板门、没有门洞），不能看起来像能进却没有落脚处。必经之路不得窄于已声明的最小值，也不得在没有目的地或指引物的地方断头。按精灵外接框的中心来摆不够：门洞的屋顶比立柱宽时，墙仍要接到立柱的实体，不能停在更宽的檐下。

记录方式与 [一致性检查](consistency-review.md) 相同：写文件或画面位置、预期（合同或场景计划原文）、观察到的事实、状态。没有叠过审查层、也没有按计划核对类型要素或已声明的接头时，写 `UNDETERMINED`，不要凭印象写成通过。

## 4. 什么算不合格

出现下列情况应退回，即使单件单独看“像那么回事”，即使色板、尺寸和视角基准线检查已经通过。下列条目由人看图判定；脚本不给通过或失败，除非另外提供了可行走蒙版——即便如此，那也只是可达性数据，不是画面评分。墙与开口的接头也一样：即使场景计划写了 `joints`，脚本也不量缝，不判接上或断开：

- 门开进水里，或开到画布边缘，门前没有合同要求的净空。
- 必经之路窄于已声明的最小宽度，或走廊在中途收成一条缝。
- 已声明的类型要素缺失：例如门院没有门洞或没有围合的墙篱，临水埠头没有临岸通路、没有可走的石阶或坡道，或码头背向来路。
- 墙、篱或绿篱接到门、门洞或立柱时，接触按实体算，不按整张精灵的外接框算。屋檐、出挑和透明边距都不算接上。墙端和立柱之间露出地面、院地、天空或其他背景，应退回。
- 墙体顶到立柱，却仍留着独立的端头收边。墙身和端头应收进立柱：要么与立柱实体重叠、由立柱画在上层，要么改用专门的接头砖。
- 同一道墙的各段也要这样相接。转角件和直墙之间露出背景，同样不合格。
- 动线混杂或被阻断：主路到不了门、码头或院门。
- 道具、植物或碎石占了门前净空，或压在预留的站立格上。
- 物体悬空或陷入地面，脚底对不齐落地的格子。
- 石阶被压成看不出踏步的条纹板，无法读成可攀爬的台阶。
- 建筑被画框切掉，或基础离地图边近于合同。
- 可互动物件之间近于已声明的间距，站位重叠。

视角基准线确认的是机位、透视和尺度。本页确认的是摆放与动线。一件东西透视正确，仍可能挡门、悬空或打断来路；一条路左右边平行，仍可能没有院门，或走到一半就断在墙根。

## 5. 与其它部分的关系

- 仓库里若有 [视角与透视确认基准](camera-baseline.md)，先用那一页确认投影，再使用本页。不要把路宽和门前净空写进视角页，也不要在本页重判消失点。
- 先继承 [主题合同](theme-cohesion-contract.md)，再填本页的结构化布局。不要为此修改 `project_theme.projection.world`，不要在主题合同里新增关键字段；`schema_version` 保持为 1。
- [风格设计](style-design.md) 里的空间与摆放要写到能出路宽、净空和类型要素，而不是停在“留出空地”这类形容词。
- 像素尺寸、色板、alpha 仍用 [机器检查合同](../assets/templates/audit-contract.json)。不要把“路是否走得通”、“有没有院门”或“墙有没有接到立柱”塞进现有 `audit_assets.py` 的未知字段，也不要声称存在自动摆放评分。
