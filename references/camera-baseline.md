# 视角与透视确认基准

在制作、扩展或复盘世界场景、建筑、地形，以及要摆进场景的道具时阅读本页。本页说明如何把项目的投影写成可叠加的基准线，并在单件和合成稿上确认机位没有混用、也没有意外透视。它不替代 [一致性检查](consistency-review.md) 或 [主题合同](theme-cohesion-contract.md)，也不给画风打分。基准线只用于审查，不画进游戏成品。

现有美术规范和主题合同里可以写投影，但若只留下“俯视”“3/4”这类空泛描述，审查时没有可对齐的格子和铅垂线，地面和建筑就容易各用一套机位。道路向上收窄、竖线倾斜、同组屋顶顶面比例不一，都应在叠上基准线后被看出，而不是等整张场景拼完再凭印象判断。

## 1. 先把投影写成可出图的合同

在批量生成世界素材之前，先填 [美术规范模板](../assets/templates/art-bible.json) 的 `projection`。未确认的字段保持 `null`，不能由模板或模型提示词猜一个倾角。主题合同里的 `projection.world` 仍是给项目看的文字摘要；结构化字段以美术规范为准，两处矛盾时先停下来，不要默认为新生成图是对的。

至少要能回答下面这些问题，才能画出基准线：

| 字段 | 要写清的内容 | 不写清楚时会发生什么 |
|---|---|---|
| `kind` | 正交正面俯视（可见立面与顶面）、正交纯俯视、等距，或真透视（一点/两点） | 每个任务各自发明一个俯视角度 |
| `vanishing` | `none`，或一点/两点及消失点大致位置 | 正交项目里出现向上收窄的路和房 |
| `verticals` | 通常保持垂直；只有项目明确使用倾斜竖直边时才例外 | 墙柱东倒西歪却被当成风格 |
| `visible_planes` | 世界物体应看见哪些面，例如正面加顶面、不许露出侧面 | 有的房子露侧面，有的只露正面 |
| `ground_edges` | 地面、道路、岸线在画面深度上是否保持平行等距 | 地面用透视，建筑用正交，合成时对不齐 |
| `front_to_top_ratio` | 同组建筑可见立面与可见顶面的大致高度比 | 屋顶有的扁、有的高，像换了相机 |
| `baseline` | 格宽、角色身高、层高、叠加层画布大小，单位是逻辑像素 | 有格子也无法核对尺度 |

已有项目必须先从已接受的参考资产量这些值，再写进合同，不能按新提示词重选。UI 正面框体、图标简化投影可以是用途例外，但要单独记录，不能让世界场景跟着 UI 变成正视。

换共同投影属于主题修订：更新版本，并复查已有世界资产，不要把新机位藏在单条提示里。

## 2. 基准线是审查叠加层，不是场景里的线

基准线是一张透明图，叠在原尺寸或整数倍近邻放大的素材、联系表和场景合成稿上。推荐分色，避免和画本身混淆：

- 地面网格（青）：表示地面深度与左右方向。正交时，向画面深处的边保持平行、间距均匀，**上下两端一样宽**，不画成梯形。等距时用项目规定的菱形格（常见 2:1，以合同为准）。真透视才画地平线与通向消失点的放射线。
- 铅垂线（黄）：竖直边应与这些线重合。
- 尺度尺（品红）：一格、角色身高、一层檐口的高度记号。
- 体积线框（白）：一栋示意建筑的可见立面和顶面，用来核对 `front_to_top_ratio`。它不是可做进游戏的房子。

项目若是正交，就不要在基准线上放一条暗示透视的地平线。代码可以画出这张审查叠加层，也可以在编辑器里做同样的调试网格；二者都不是设计图，不能进正式画面，也不能用来给模型当参考图。

用本 skill 的脚本从已填写的规范生成叠加层：

```bash
python3 scripts/camera_baseline.py --bible /path/to/art-bible.json --out /tmp/camera-baseline.png
python3 scripts/camera_baseline.py --kind orthographic-front-top --size 480x270 --unit 16 --character-height 32 --out /tmp/camera-baseline.png
```

字段仍为 `null` 时，脚本应拒绝出图并说明缺什么，不能默认为某种俯视。示例合同和示意叠加层见 [camera-baseline 示例](../examples/camera-baseline/README.md)。该脚本只负责把已确认的投影画成格子，不给图像自动判定通过或失败。

## 3. 何时叠、怎样看

1. 世界或场景成组出图前，先冻结合同并生成一张与目标逻辑画布（或视口）同尺寸的基准线。同一项目修订只保留这一套，不按单件另出一套倾角。
2. 提示词引用同一合同：写清有无消失点、竖线是否垂直、应看见哪些面。不要在每个任务里重写相机。
3. 先把单件（原图和像素化结果）放在基准线上核对，再看整张合成。只看单件合格不够。
4. 地面、水体、道路与建筑、树木必须叠在**同一张**基准线上。地面是整张缩放的底图时尤其要查左右边是否平行，这是整张底图最容易混入透视的地方。
5. 在最终显示倍率下看一次落地和尺度；缩略全图只能看布局，不能代替原尺寸核对。

记录方式与 [一致性检查](consistency-review.md) 相同：写文件或画面位置、预期（合同原文）、观察到的事实、状态。没有叠基准线就写 `UNDETERMINED`，不要凭印象写成通过。

## 4. 什么算不合格

出现下列情况应退回，即使单件单独看“像那么回事”，即使色板和尺寸检查已经通过：

- 合同写明无消失点，但道路、屋脊、岸线或地面左右边向深处收窄或张开。
- 墙、柱、树干等应垂直的边明显倾斜，或左右两端的铅垂关系不一致。
- 同组建筑的可见顶面比例明显不同，或有的露出侧面、有的不露，且没有记录例外。
- 一张合成稿里，地面、建筑、道具不在同一套格子上（机位混用）。
- 物体相对尺度尺明显跳变：门比角色矮一截、码头脚柱高过小屋等，又不是有意的设计。

基准线确认的是机位、透视和尺度。它不代替摆放与动线审查：一件东西透视正确，仍可能挡门、悬空或打断来路。动线、门前净空和地标位置按项目自己的布局规范另查。

## 5. 与其它部分的关系

- 先继承 [主题合同](theme-cohesion-contract.md)，再填本页的结构化投影；改变共同投影要升主题版本。
- [风格设计](style-design.md) 里的“投影与尺度”要写到能出基准线，而不是停在风格形容词。
- 像素尺寸、色板、alpha 仍用 [机器检查合同](../assets/templates/audit-contract.json)。不要把“有没有消失点”塞进现有 `audit_assets.py` 的未知字段，也不要声称存在自动透视评分。
- 游戏 UI 框体常用正视正交，与世界投影不同是允许的用途差异，见主题合同；不要把 UI 正视网格套到世界场景上，也不要把世界 3/4 网格套到面板上。
