# 同一主题下的美术与 UI 一致性合同

适用于同一游戏的场景、角色、道具图标、界面、文字，以及同主题的不同界面方案。这里的“统一”需要明确的继承关系和可复核证据；把每张图分别选成“好看的风格”，即使各自质量不错，也可能拼不成同一个世界。

本文件是本库的制作约束与审阅方法，不是统计学审美模型。使用 [主题合同模板](../assets/templates/theme-contract.json)，配合已有 [美术规范](../assets/templates/art-bible.json)、[UI 设计合同](../assets/templates/ui-design-contract.json) 和 [一致性检查](consistency-review.md)。模板是供 agent 读取和维护的数据，不是已经接入脚本的自动规则引擎。

## 先继承，再描述差异

```text
项目主题与版本
  ├─ world：场景、建筑、地形的用途约定
  ├─ character：角色的用途约定
  ├─ item-icon：识别和比较物品的用途约定
  ├─ UI：框体、控件、状态反馈的用途约定
  └─ typography：文字内容和显示的用途约定
       ↓
单个资产 / 界面：继承对应角色，仅记录必要且可解释的例外
```

采用以下规则：

1. **项目规范是共同来源。** 记录主题 ID、版本、参考资产和文件哈希。先读取当前规范，再生成、挑选、修复或引入素材。不能因本次任务是“画按钮”就重新选一套画风。
2. **role 只描述用途差异。** 角色、建筑、图标不必同画布或同大小。UI 正面框体可以不同于世界俯视投影，但要记录差异原因、继承项、适用范围和复验方法。
3. **单素材不自行改主题。** 色彩角色、主光、投影、轮廓语法、材质和像素策略都先继承。需要偏离时先写例外记录；缺少理由或证据时标记 `UNDETERMINED`，不能默认为“新风格也可”。
4. **例外不是全局重定义。** UI 图标的识别夸张不允许连带改变世界资产比例；一处火焰的局部光不改变全场景主光；账本结构变化不允许购买/错误的颜色语义随方案交换。
5. **例外必须能收回。** 写明资产或角色范围、覆盖的具体字段、原因、证据、限制及复验条件。不要用“更好看”覆盖一组没有审查过的规范。例外失效或冲突时回到父级约定。
6. **改变共同规范时更新共同版本。** 若确需换整个项目的色板、视角或像素密度，应明确记录为主题修订并检查受影响资产，不把它藏在单张图片的提示词里。用户已确定的要求不能被后续 agent 静默覆盖。

这是 agent 的工作流程，不新增逐次向用户审批的要求；已有任务授权内的实现选择可以记录理由后执行。遇到与用户明确要求冲突的变化，仍应以用户要求为准。

### 数据如何解释

- `project_theme` 是共同约定；`roles` 的每项默认继承它。
- `overrides` 只保存明确覆盖项，必须含 `field`、`value`、`reason`、`evidence`、`review_status`。未出现的字段继续继承。
- `null` 表示未知，不代表通过、不代表可以另选风格，也不自动禁用父级约束。
- 单资产 `exception_ids` 引用集中登记的例外；一条例外不能隐式影响其他资产。
- `field` 使用可阅读的点号路径说明覆盖位置；本模板未提供自动合并或执行该路径的 API。
- 来源或截图发生变化时，依赖旧哈希/旧构建的结论需要复查。已经测量过旧图，不等于新图仍然通过。

## 同一主题不等于同样大小或同一层细节

统一的是识别语义与共同的美术规律；角色用途可以决定尺度和抽象程度。

| 跨角色关系 | 应保持 | 可以有理由地不同 |
|---|---|---|
| 世界物品 ↔ 背包图标 | 关键轮廓、颜色身份、材质含义、同一物品对应关系 | 图标可放大辨识部位、减少细纹、改为更易读的投影；不要要求图标等于世界截图缩小 |
| 世界建筑 ↔ UI 木框 | 木材的暖冷关系、粗糙/磨损语法、明暗层级 | UI 木纹更稀疏，文字区更平静，框体采用正交正面 |
| 世界角色 ↔ 角色头像 | 身份特征、服饰颜色和材质、年龄与气质 | 肖像可有更多表情细节；不能无记录地换成另一种渲染流派 |
| 纸面菜单 ↔ 柜台账本 ↔ 轻量面板 | 商品图、中文字段、状态语义、共同色彩与材质 | 信息布局、纸面组织、物件隐喻和界面占地不同 |
| 像素标题 ↔ 长中文说明 | 字体角色、层级、色彩语义、语言内容 | 标题可用像素字体整数倍；长说明可用明确记录的清晰正文层，需看实际屏幕效果 |

世界中的一粒种子和商店中的商品图没有必要占相同数量的屏幕像素。比较时应检查“同用途、同最终显示大小”的图标，或把物体放回其实际场景，而不是把所有原图一律拉成同尺寸再判定。

## 共同约束应写到哪一层

| 项目 | 必须记录 | 审阅证据 |
|---|---|---|
| 色彩角色 | 世界基调、基底/阴影/亮部，UI 文字/主行动/焦点/危险；哪些是具体色值，哪些是视觉关系 | 源色值、状态对照、明暗背景合成。UI token 不是整张场景图的有限色板 |
| 光源 | 主光方向、环境光、投影规则、发光/局部光例外 | 同材质物体的亮面与投影；图标与世界并排观看 |
| 投影与尺度 | 世界投影、可见平面比例；角色门高关系；UI/图标的用途覆盖 | 场景合成与同族联系表，不由提示词代替观察 |
| 材质语法 | 木、纸、石、布、金属的高光宽度、粗糙感、纹理密度和破损尺度 | 对应材质局部与整屏，避免所有材质共享同一种高光噪声 |
| 边缘与细节频率 | 内外边线、台阶节奏、细杆/孔洞、每单位显示面积的细节密度 | 原坐标放大与实际大小；世界与 UI 可以密度不同，但差异应有用途理由 |
| 像素策略 | 源图尺寸、目标逻辑网格、导出倍率、显示采样、硬 alpha 或特效例外 | 实际导出与渲染。`image-rendering: pixelated` 不能把软边原图认证为原生像素素材 |
| UI 内容层 | 价格、数量、正文保持可变；框体只承担材质和边界，预留静区 | 最长真实中文、最大数字、禁用/错误/成交状态，不能只看空面板 |
| 状态反馈 | 当前选择、键盘焦点、悬停、主要动作、危险/错误、成功各自规则 | 同一动作跨方案/屏幕对照；不能只凭颜色区分，也不能把高亮当作焦点证据 |
| 字体与屏幕 | 字体文件/来源/版本/许可/哈希；文字角色与最终屏幕尺寸 | 真实字形、缺字、换行、重叠；CSS 字号需结合祖先缩放与显示倍率 |

不同方案可以表达同一主题，却不能给每张商品图、每种按钮、每个状态重新分配任意的配色或材质。确定 role 差异后，下游 agent 应按同一套规则制作下一件，而不是从配方列表重新挑选。

## 技术门槛与视觉审阅分别结论

硬性技术项只在明确期望值和实际测量范围内判定：文件能否解码、画布尺寸、图集切格、alpha、已固定色板、导出倍数、字体文件与许可等。没有配置逻辑网格时，不能给“网格一致”写通过。

对于目标为严格原生像素素材的交付：

- 只有“看起来像像素画”的高分辨率源图，**不是已经完成的原生像素导出**。
- 存在软边、半透明物体边缘或未固定的有效像素格，需要独立处理与验收。其界面样张价值和生产适用性是两个结论。
- `grid_scale=1` 不会识别隐藏像素网格；`grid_scale=N` 只检查明确 N 倍导出块的像素重复，不评审台阶节奏。
- 若合同要求硬 alpha，非 0/255 的 alpha 就是不符合该项；不能因为透明背景请求成功而改写为通过。
- 文件尺寸相同、颜色数量接近、同一个生成模型、同一组提示词，都不能证明画风一致。

视觉项需要打开原图、同倍率联系表及实际合成截图，观察投影、色彩关系、材质、边缘节奏、内容与背景竞争。整体结果不取各项平均分；机器全过仍不能替代视觉验收。

## 可执行的审阅矩阵

这里的“可执行”指审阅人能按步骤复验，不表示已有自动主题评审器。每一行都写六项：

| 字段 | 要写的内容 |
|---|---|
| `evidence` | 原文件/截图/构建/测量记录；注明哈希、窗口、显示倍率与状态，缺少则留空 |
| `expected` | 共同合同中对应的规则；不能临时按图改标准 |
| `observed` | 实际看到或测到的事实；没有打开图就不编造观察 |
| `status` | `OBSERVED_PASS` / `OBSERVED_FAIL` / `UNDETERMINED` / `NOT_APPLICABLE` |
| `exception` | 例外 ID 或 `null`；例外依据、边界和生产适用性单独登记 |
| `method` | 复验动作，例如“同坐标 4 倍近邻比较图标外轮廓，再查看其 48 px 实际显示” |

执行顺序：

1. 冻结主题版本与资产哈希，列出本轮涉及的 role 和例外。
2. 逐文件核验技术项；没有标准时写 `UNDETERMINED`，不要默认绿色。
3. 按用途组成联系表：图标对图标、框体对框体，再看跨角色合成。
4. 使用真实文字、最密集状态与失败状态，分别查看每种界面。
5. 对同一动作核对内容、状态语义及数据；布局可变不等于机制可变。
6. 记录问题、影响、修复目标和复验条件。修改后只复查受影响项，旧证据失效时明确标记。

这种分层采用了本库既有的 [设计基础](ui-design-foundations.md) 和 [UI 审查协议](ui-evaluation-method.md)：静态观察、原型走查与真实玩家研究各有证据范围，不用不存在的“美术总分”合并它们。

## 与现有检查脚本的衔接

`theme-contract.json` **不能直接作为** `scripts/audit_assets.py --contract` 的输入。现有检查器只接受 [audit-contract.json](../assets/templates/audit-contract.json) 所列的技术字段，例如 `canvas_size`、`grid_scale`、`alpha_policy`、`palette`、`margins`。

从主题合同中挑出已明确的技术值，另建实际项目的 audit 合同；人工确认 role 对应关系，再运行现有脚本。需要新增主题语义、光照或材质检查时，先做人工审阅，不向脚本塞入未知字段，也不声称存在自动“主题相似度” API。

可核验的示例见 [青禾种子铺主题合同](../examples/rural-shop-demo/theme-contract.json)。它区分同主题的三种结构方案、已验证的源文件信息，以及仍未通过的严格像素生产项。

## 校验继承关系与证据记录

提供标准库脚本检查可机械判断的内容：

```bash
python3 scripts/validate_theme_contract.py /path/to/theme-contract.json --json
python3 scripts/test_theme_contract.py
```

`validate_theme_contract.py` 始终输出 JSON。它检查主题 ID、已声明角色、资产所属主题/角色、覆盖理由与证据、例外引用和范围、文件哈希及记录完整性。不做图像语义分析，也不替审阅人认定某张图片“好看”。资产不能通过增加内联 `palette` 或 `style` 字段绕过项目规范。

- `structure_status` 表示合同结构与继承引用是否有效。
- `completion_status` 表示关键参数和审阅记录是否齐全。
- `recorded_visual_status` / `recorded_runtime_status` / `recorded_strict_pixel_production_status` 是合同中已记录的分层结论，不是脚本新做的视觉或运行测试。
- 退出码 `0`：本次记录完整且没有失败；`1`：结构错误或已有明确的硬技术失败；`2`：没有明确失败，但关键决策或证据不完整。

例如，当前青禾商店可以同时得到 **结构 PASS、记录 INCOMPLETE、视觉 UNDETERMINED、严格像素生产 OBSERVED_FAIL**；最后一项来自原始图集的实测 alpha。原型用途例外不会把它改成通过。修改源文件后，旧哈希对应的结论会被标记为待复查。
