# 同一个乡村商店任务，怎样从设计理由走到界面

这是整理者编写的方案比较与设计简报，现有 [三个可运行界面小样](rural-shop-demo/README.md) 可配合阅读。小样使用明确标记的独立演示数据，不代表已有游戏机制或目标玩家实验；运行证据及范围见小样README。引用案例用于观察方法，不直接复制其美术资产。接入实际项目时，价格、容量、时间规则和交易机制必须来自该项目。

本文随 v1.3.1 重做版更新。上一版虽然有交易测试，用户仍明确否定视觉效果；这不是可以用测试通过数量抵消的问题。原始交互证据继续保留，本次重新审查文字密度、材质和方案结构。

## 任务与内容先于皮肤

任务：玩家比较两种种子，判断当前资金是否足够，选择数量并完成购买，之后回到农场。

不可缺少的内容是：商品身份、实际用途与种植约束、持有量、价格规则、购买数量、总成本、资金缺口、容量限制、购买后结果，以及确认/取消动作。若项目没有某个机制，不为填满 UI 新增它。

这些内容至少形成三个可比较的组：**候选商品与当前选择 → 当前选择的效果和限制 → 这次交易的成本与结果**。把全部商品介绍塞进列表会使比较困难；只显示图标和价格又不足以理解约束。使用列表/网格配独立详情是一个候选结构，仍需按商品量和目标输入决定。

## 比较三个方案

| 方案 | 视觉与世界关系 | 可借鉴的优点 | 必须付出的代价 |
|---|---|---|---|
| 木框纸面菜单 | 材质暗示；面向玩家的屏幕叠加 | 内容面积稳定、文字与数量易对齐；可参考 Moonlighter 的列表/详情分工 | 不因木材质就成为世界内 UI；厚边可能占用阅读空间 |
| 柜台账本 | 物件隐喻；是否属于虚构世界需由剧情/机制确定 | 若账本确实属于商人，可能加强角色和交易情境 | 透视、翻页、遮挡与文字尺寸可能妨碍频繁买卖；需决定是否允许快速操作 |
| 世界入口 + 轻量交易面板 | 空间锚定入口，交易阶段改为屏幕叠加 | 保留 NPC 和地点关系，密集比较时给足面积 | 两阶段的输入、镜头、世界时间、退出与焦点恢复必须一致 |

三者没有统一排名。对“世界占主要画面、需要中文和手柄”的项目，可先比较第三种与第一种的小样；这是基于约束的设计假设，并非实证结论。不能仅凭“更沉浸”排除可读叠加层。

## 现有小样怎样保持可比较

[运行与审核说明](rural-shop-demo/README.md) 提供 A 木框纸面、B 柜台账本、C 世界入口与轻量面板。三者同属一个乡村主题，共用 6 种商品、同一商品图集与交易状态；布局切换不会另起一套资金或库存。初始为 240 钱、背包 9/24 格，每份商品占 1 格是明示的演示简化，详见 [数据合同](rural-shop-demo/data-contract.json)。种植季节是商品说明，不额外禁止购买。

v1.3.1 不再把三种方案当成完全相同的信息表单：A 保留列表与商品详情；B 的右页改为“本次购入”账目，将种植/使用条件改为精简真实摘要，突出商品身份、数量、花费和余额；C 改成最大宽 870px 的底部短交易窗，使用 3×2 商品格和独立交易区。C 格子使用中文短名，详情及可访问标签保留完整名称。B 直接显示真实种植/使用条件摘要，包括成熟天数、水田要求与施肥条件；不同方案的信息呈现仍应按任务取舍记录。

读取 [本例主题合同](rural-shop-demo/theme-contract.json) 时按项目主题 → `world/character/item-icon/UI/typography` 用途规则 → 有据例外继承。A/B/C 有意比较阅读结构和世界入口，不为每种方案另换商品风格。纸面、账本与轻量面板沿用共同木纸材质、色彩角色和商品身份；购买按钮共用绿色主要行动语义，锈红保留错误/风险。

本版取消原金色宝石角框。A/C 的新朴素面板采用源图 24px 切片、8px 显示边框；账本桌面保留物件背景，窄屏改用同家族纸面。主阅读层级为身份 24px、决策重点 18px、阅读 14px、辅助 12px：Fusion Pixel 限定在店名等身份标题，商品与交易内容主要用系统中文；账本条件摘要采用12px系统中文辅助角色。比较工具个别 10–12px 文字在主阅读区之外。字体表只表达分工，仍需在原生窗口检查完整中文、对比与密度。

仓库保留 5 张 AI 生成 PNG：原四图见 [素材记录](rural-shop-demo/assets/asset-provenance.json)，新增朴素面板的一次生成及原图记录见 [新面板来源](rural-shop-demo/assets/plain-panel-provenance.json)。旧 `wood-panel.png` 仅作历史源图，已退出当前界面。字体来源及全部 OFL 声明继续保留。图集存在软 alpha，严格硬 alpha 门槛失败，有效逻辑像素网格仍未固定；UI 重做不改变这些生产限制。`validate_theme_contract.py` 只检查合同结构、引用和已记录证据，不自动证明这三屏视觉一致或某种方案更好。

## 本例的待验证候选

- 系统模式：`shop-trade`，必要时联合 `inventory-equipment`。
- 视觉语言：低纹理纸面与有限木框；不是每个数字单独一个厚边框。
- 世界关系：面向玩家的交易面板；入口属于世界，不声称交易面板本身是场景里的物件。
- 内容密度：交易时集中比较；平时关闭，保留世界。
- 表意：价格、缺口、容量必须有文字或数字，红绿仅作为辅助。
- 时间策略：由项目规则确定。若世界继续运行，必须提供风险提示和可及时退出的路径；不能偷偷暂停已定义为实时的游戏。
- 输入：分别描述指针与焦点导航。选中商品和当前焦点可并存；切换输入后不丢选择。

## 状态和真实内容

正常可买、资金不足、容量不足、未解锁、已售罄与正在执行交易不是同一种灰按钮。它们需要各自的可读原因与下一步。静态图中只能观察外观，仍需实现并测试操作反馈。

本次可运行小样范围是正常购买、资金不足、满背包、售罄、非法数量与成功后的扣款/入包反馈，并提供审核场景和恢复按钮。未解锁、世界时间推进、游戏存档等属于接入项目时核对的条件，不能因上面的通用状态清单而声称小样已实现。验收以小样README的实际记录为准；浏览器走查不等于手柄或目标玩家测试。

试稿使用项目最长真实中文商品名、多行约束、最大合理数字与当前余额临界值。正文保持可变文本层，装饰素材只处理框、底和图标。若出现拥挤，先调整内容顺序、详情区或分页，不把整个 UI 非整数缩小。

## 验收而非好看打分

检查玩家能否在确认前理解商品差异、这次花费与失败条件；操作后能否确认实际结果；取消是否回到原任务；手柄是否全程可达；最亮和最暗世界背景上是否都可读。用同一条件比较候选方案，记录错误与回退，不预设哪个方案一定更快。

交付填写后的 [UI设计合同](../assets/templates/ui-design-contract.json)、真实内容画面和输入路径，按 [审查协议](../references/ui-evaluation-method.md)记录观察与未验证项。

本次桌面预览使用原生 1280×720，窄屏审阅为 390×844。新版证据见 [v1.3.1 审阅记录](../validation/UI-REVISION-V1.3.1.md)，[v1.3 历史报告](../validation/SHOP-COHESION-V1.3.md) 保留为此前状态记录。不能以“测试通过”替代对新截图的观察，也不能在用户尚未认可时宣称视觉问题已经解决。
